# Bybit Funding Monitor

Монитор ставок финансирования (funding) на USDT-перпетуалах Bybit для
**дельта-нейтральной стратегии**: купить спот + зашортить перпетуал на ту же сумму.

Пока ставка funding положительная, шорты перпа получают выплату от лонгов каждые
4–8 часов. Цена актива при этом не важна: спот-лонг и perp-шорт гасят друг друга,
позиция нейтральна к направлению рынка.

Монитор использует **только публичные эндпоинты** Bybit API v5. Исполнитель
(`funding_executor.py`) уже торгует на **testnet** под API-ключами (игрушечные
деньги) и ведёт память самообучения по своим сделкам.

## Запуск

Нужен только Python 3.9+ (никаких зависимостей, даже `requests` не нужен):

```bash
python3 funding_monitor.py                       # базовый отчёт
python3 funding_monitor.py --top 20 --capital 5000
python3 funding_monitor.py --symbols BTCUSDT,ETHUSDT,SOLUSDT
python3 funding_monitor.py --watch 60            # автообновление каждые 60 мин
python3 funding_monitor.py --json snapshot.json  # сохранить снимок данных
```

Полезные флаги:

| Флаг | Что делает |
|---|---|
| `--top N` | сколько символов в топе (default 12) |
| `--min-volume X` | фильтр по обороту 24ч, $M (default 5) |
| `--min-oi X` | фильтр по открытому интересу, $M (default 5) |
| `--capital X` | депозит для оценки дохода, $ (default 1000) |
| `--hold-days X` | срок удержания для амортизации комиссий (default 30) |
| `--spot-fee / --perp-taker-fee / --perp-maker-fee` | свои комиссии |
| `--max-slip-bps N` | защита от проскальзывания: остаток ордера исполняется IOC-лимиткой по границе bid/ask ±N б.п. (default 15 = 0.15%, 0 — выключить). На ВХОДЕ: не вышло в границу — вход отменяется (и откатывается уже открытая нога), а не покупается по любой цене. На ВЫХОДЕ: незакрытый остаток добирается маркетом с алертом — застрять в позиции хуже слиппеджа |
| `--integrity-every N` | сверка фактических ног на бирже с `position.json` раз в N сек (default 60, 0 — выключить): при расхождении — алерт в лог и Telegram, при восстановлении — подтверждение |
| `--max-positions N` | сколько пар держать одновременно (default 1 = одна позиция). Новая пара получает `min(--capital, свободная маржа / 1.1)`; меньше $50 свободной маржи — пара не открывается. Закрытие: `close --symbol X` / `close --all` |
| `--no-exchange-stop` | не выставлять биржевой стоп-лосс на перп-ногу (по умолчанию **выставляется** — страховка на случай, если бот/VPS не работают; цена = вход × (1 + `--max-margin-risk`/100)) |
| `--preset hold/spike/mainnet` | режим фильтра: `hold` — устойчивая ставка 30д (удержание неделями), `spike` — охота на аномалии по текущей ставке (окуп ≤ 3д, OI ≥ $50M), `mainnet` — реальные деньги: min_apy30 ≥ 15%, fast_apy ≥ 6%, окуп ≤ 10д, OI ≥ $30M — запас на комиссию круга ~0.31% |

### Режимы: paper / testnet / mainnet

| режим | что делает | ключи |
|---|---|---|
| `paper` (default) | симуляция на данных mainnet, ордера не отправляются | — |
| `testnet` | реальные ордера на testnet.bybit.com | `BYBIT_TESTNET_API_KEY/SECRET` |
| `mainnet` | РЕАЛЬНЫЕ деньги: `api.bybit.com` | `BYBIT_API_KEY/SECRET` |

Переход на mainnet:

- вход/выход требуют флага **`--confirm-live`** — без него `enter` откажет, а watch
  останется наблюдением (сигналы в лог/Telegram без ордеров);
- перед входом плечо выставляется ЯВНО (`/v5/position/set-leverage`): иначе новый
  символ возьмёт дефолт биржи и расчёт маржи/риска разойдётся с `--leverage`;
- ключи mainnet — **без права вывода** и с IP-whitelist сервера;
- берите пресет `--preset mainnet` (пороги с запасом на комиссию круга).

**Изоляция памяти по режимам:** обучающие функции (calibrate, autotune,
entry_mode) считаются только по сделкам ТОЙ среды, где работает бот —
синтетические ставки и проскальзывание testnet не переносятся на mainnet.
Пороги и profit-сдвиг живут в секциях пресетов (`mem["presets"]`). Стоп-лист
символов намеренно общий: убыток символа в одной среде — сигнал и для другой.

**Пресет-изоляция порогов:** калибровка/автотюнинг каждого пресета живут
в `mem["presets"][<пресет>]["calibration"]` отдельно. Пороги, выученные на
testnet-данных (синтетические ставки, нулевые комиссии), молча не применяются
к mainnet и наоборот — каждый пресет учится только на своих сделках.
До первой собственной калибровки фильтр берёт дефолты пресета.
| `--min-apy30 X` | порог вердикта: мин. APY, % (hold: 10, spike: 30) |
| `--min-pos X` | порог вердикта: мин. доля плюсовых интервалов 30д, % (default 80) |
| `--min-basis X` | порог вердикта: мин. базис перп/спот, % (default 0) |
| `--max-breakeven X` | порог вердикта: макс. окупаемость входа, дней (default 14) |
| `--pass-oi X` | порог вердикта: мин. OI, $M (default 20) |
| `--json FILE` | сохранить полный снимок (для истории наблюдений) |
| `--watch N` | режим мониторинга, обновление каждые N минут |

Флаги исполнителя (`funding_executor.py`): `--mode paper/testnet`, `--capital`,
`--leverage`, `--interval` (сек, для watch), `--no-auto`, `--ws` (WebSocket-лента),
`--no-learn` (выключить память самообучения), `--no-notify` (без Telegram),
`--fast-apy`, `--fast-top` (8), `--prefilter` (60 — полный скан и база подписок WS),
`--min-volume`/`--min-oi` (3 $M — предотбор), `--pass-oi` (10 $M — вердикт;
в пресете hold 20), `--maker-wait` (6 с на maker-лимитку), `--taker-only`,
`--max-spread` (0.5%), `--min-depth`, `--max-margin-risk`, `--full-every`,
`--exit-neg`, `--max-loss`, `--report-every` (минуты между отчётами о доходе
в лог и Telegram; default 60 = раз в час, 0 — выкл.),
`--daily-report-at` (ЧЧ:ММ ежедневной сводки, default 00:00, `off` — выкл.),
`--report-tz` (часовой пояс отчётов: `Europe/Moscow` или сдвиг `+03:00`;
пусто — время сервера), `--strategy funding/scalp`, `--scalp-symbols`,
`--scalp-interval`, `--scalp-fast`/`--scalp-slow`, `--scalp-tp-bps`,
`--scalp-sl-bps`, `--scalp-max-hold`, `--scalp-fee-bps` — подробности в `--help`.

## Что означает каждая колонка

- **ИНТР** — периодичность выплат funding (4ч/8ч).
- **СТАВКА** — ставка за ближайшую выплату (0.01% = 1 bp).
- **APY 7д / APY 30д** — средняя годовая ставка за окно. 30д — консервативная оценка.
- **+30д** — доля интервалов с положительной ставкой (100% = платили всегда).
- **БАЗИС** — насколько перп дороже (+) или дешевле (−) спота. Для выгодного входа
  нужна премия перпа (≥ 0): шортим дорогое, покупаем дешёвое. `нет` = спот-ноги
  на Bybit нет — классический хедж невозможен (частый случай у монет с самой
  высокой ставкой: перпов на бирже больше, чем спот-пар).
- **ВХОД** — полная стоимость круга: комиссии taker + спреды обеих ног
  + невыгодный базис, % от нотиона.
- **ОКУП** — за сколько дней средняя ставка 30д отобьёт стоимость ВХОДа.
  `∞` = ставка не плюсовая.
- **OI / ЛИКВ** — открытый интерес ($) и уровень риска: высокая (OI ≥ $100M)
  / средняя / НИЗКАЯ.
- **ВЕРДИКТ** — прошёл бы символ фильтр бота: `✓ ГОДЕН` или `✗` с причинами.
  Пороги настраиваются флагами `--min-apy30/--min-pos/--min-basis/--max-breakeven/--pass-oi`.

## Как читать результат (честно)

Отчёт показывает три портфеля:

1. **✅ Прошли фильтр** — символы с вердиктом `ГОДЕН`: то, что бот держал бы
   прямо сейчас. Пустой блок — нормальное состояние: фандинг-арбитраж это игра
   ожидания окон, в тихом рынке бот должен сидеть в стейблкоинах.
2. **Топ-список (агрессивно, без фильтра)** — символы с максимальной средней
   ставкой. Там будут микрокапы с APY в десятки процентов. Это НЕ «бесплатные
   деньги»: сверхвысокая ставка — компенсация за риск делистинга, тонкого
   стакана, разворота ставки в минус и ликвидации perp-ноги на скачке цены.
3. **Мейджоры (консервативно)** — BTC, ETH, SOL и т.п. Ставки заметно ниже,
   зато ликвидность глубокая и история устойчивее. Это реалистичный ориентир.

Помните: **высокий funding по всему рынку часто сопровождает перегретые фазы**
(толпа агрессивна в лонгах). Именно тогда ставка и разворачивается. Среднее
за 30 дней — взгляд в прошлое, а не прогноз.

## Экономика сделки

Комиссии (non-VIP, сверяйте с актуальной таблицей Bybit):

- спот: ~0.10% (maker и taker)
- перпы: 0.055% taker / 0.02% maker

Цикл «вошёл taker → вышел taker» стоит ~0.31% от депозита (две ноги × две стороны).
При средней ставке funding это окупается за дни-недели удержания; при частой
ротации позиций комиссии съедают прибыль — поэтому стратегия любит «редко входить,
долго держать, менять позицию только при смене знака/просадки ставки».

Также учтите:
- на perp-ноге нужен **запас маржи** (буфер против ликвидации при скачках цены);
- funding начисляется только если позиция открыта **на момент снимка ставки**;
- ставки имеют кап (Bybit ограничивает экстремальные значения).

## Исполнитель (funding_executor.py)

Следующий этап дорожной карты: не только смотреть, но и открывать пару
«long spot + short perp» по тем же правилам, что и вердикт монитора.

```bash
python funding_executor.py scan                # кто проходит фильтр прямо сейчас
python funding_executor.py enter               # войти по лучшему символу (auto)
python funding_executor.py enter --symbol BTCUSDT --force   # принудительно
python funding_executor.py status              # PnL, funding, neg_streak
python funding_executor.py check               # решение по выходу (kill-switch)
python funding_executor.py close               # закрыть (перп первым, потом спот)
python funding_executor.py watch              # автономный цикл, каждые 15 сек
python funding_executor.py watch --ws          # то же на WebSocket-ленте
python funding_executor.py watch --no-auto     # только сигналы, без авто-входа
python funding_executor.py void --force        # снять фантомную позицию из state
python funding_executor.py memory              # выводы памяти + пороги + журнал
python funding_executor.py memory --autotune   # внеплановый автотюнинг порогов
python funding_executor.py memory --apply-tune # применить сохранённый автотюнинг сейчас
python funding_executor.py memory --relearn    # перестроить память с нуля из bot.log
python funding_executor.py sanity              # разбор физически невозможных сделок
python funding_executor.py sanity --fix        # зафиксировать пометки в файлах данных
```

### Портфель: несколько пар (`--max-positions`)

По умолчанию бот держит ОДНУ пару (`--max-positions 1`) — поведение как раньше.
С `--max-positions N` (в config.json — `"max-positions": 3`) он держит до N пар
одновременно с тем же набором правил выхода: kill-switch'ы, целостность ног,
hold-to-N и биржевой стоп считаются и проверяются для КАЖДОЙ пары отдельно.

Что меняется:

- **состояние** — `position.json` хранит список `positions[]`; поле `position`
  остаётся зеркалом первой пары, поэтому старые файлы, health-check и внешние
  инструменты продолжают работать (старый файл читается как портфель из одной
  пары);
- **размер новой пары** — не весь `--capital`, а
  `min(--capital, свободная маржа / 1.1)`: спот-нотион + маржа уже открытых
  пар уже заняты. В `paper` эквити = `--capital × --max-positions`; в
  `testnet/mainnet` — реальное эквити UNIFIED-счёта. Если свободно меньше
  `$50` — пара не открывается (комиссии съедят такую позицию);
- **вход** — заполненный портфель и дубль символа отклоняются ДО отправки
  ордеров. В `watch` авто-вход ищет пару, пока есть свободный слот, и не берёт
  символы, уже стоящие в портфеле;
- **закрытие** — в портфеле команда обязана быть однозначной:
  `close --symbol BTCUSDT` (одна пара) или `close --all` (все сразу, с
  построчной сводкой). Без флагов при нескольких парах — отказ с подсказкой
  (не угадываем, какую пару закрывать);
- **status / stats / часовой отчёт / ежедневная сводка / панель** — все
  открытые пары построчно, включая суммарный PnL и свободную маржу;
- **health-check** — сверяет с биржей КАЖДУЮ пару портфеля и подсказывает
  `close --symbol X` для пары, которую надо поправить.

```bash
python funding_executor.py watch --max-positions 3        # портфель из 3 пар
python funding_executor.py status --max-positions 3       # все пары + свободно
python funding_executor.py close --symbol BTCUSDT --mode testnet   # закрыть одну
python funding_executor.py close --all --mode testnet             # закрыть всё
python funding_executor.py void --force --symbol BTCUSDT          # снять одну
```

Ограничения сознательные: пары одной среды (режим берётся у бота), вход не
блокирует параллельный вход бота (только предупреждение), а `--capital` остаётся
капиталом НА ПАРУ, а не общим лимитом счёта — лимит задаётся
`--max-positions` и свободной маржой.

### Автономный режим `watch` — реагирует сразу

Бот крутится сам и реагирует на ситуацию немедленно:

- **быстрый скан каждые `--interval` секунд (default 15)** — 2 лёгких запроса
  по тикерам: текущий APY ≥ `--fast-apy` (default 3%), базис ≥ 0, есть спот-нога;
  в глубокую проверку (история ставок + вердикт) проходят топ-`--fast-top`
  (default 6) кандидатов;
- **авто-вход** за 2–6 секунд после появления годного символа (выключается
  флагом `--no-auto`); после неудачного входа — кулдаун 120 сек;
- **авто-выход** по kill-switchу: funding в минусе `--exit-neg` интервалов
  подряд, убыток > `--max-loss` %, расхождение дельты ног, собрано ≥
  `--hold-payouts` успешных выплат (фиксация прибыли);
- **полный скан** топ `--prefilter` (60) кандидатов раз в `--full-every` секунд
  (default 300), чтобы fast-скан не пропустил медленно растущие ставки;
- **отчёт о доходе каждые `--report-every` минут (в config.json — 60, раз в час)** —
  в лог и в Telegram: **баланс счёта**, **PnL за день** (реализованный +
  живой по открытой позиции), открытая позиция с живым PnL и таблица
  последних закрытых сделок с итогом (цена/funding/итого, винрейт);
- **ежедневная сводка в `--daily-report-at` (default 00:00, пояс `--report-tz`)** —
  баланс счёта, итог дня (с открытой позицией) и итог недели с понедельника,
  лучшая и худшая сделка дня. День отправки пишется в `position.json`
  (`last_daily_report`): рестарт бота не дублирует сводку, а пропущенная
  из-за падения сервера уйдёт при подъёме. `off` — выключить;
- всё пишется в консоль и в **`bot.log`** (блок «События бота» на панели):
  ENTER / EXIT / HOLD-heartbeat раз в минуту — видно, что бот жив;
- исключения в цикле не убивают бота — он пишет ошибку и продолжает.


Два режима (`--mode`):

- **paper** (по умолчанию) — симуляция на ЖИВЫХ ценах Bybit, ключи не нужны,
  всё пишется в `position.json`. Безопасно для первого знакомства.
- **testnet** — реальные ордера на `testnet.bybit.com` (игрушечные деньги).
  Нужны ключи — либо в переменных окружения:
  ```bash
  export BYBIT_TESTNET_API_KEY=...
  export BYBIT_TESTNET_API_SECRET=...
  ```
  либо в файле `.env` рядом со скриптом (читается автоматически, в git не коммитить):
  ```
  BYBIT_TESTNET_API_KEY=...
  BYBIT_TESTNET_API_SECRET=...
  ```
  Ключи создаются на testnet.bybit.com → API Management, **без права вывода**.

  ✅ Проверено на testnet 06.10.2026: полный цикл `enter → status → check → close`
  (BTCUSDT, обе ноги исполняются, PnL −0.11% = комиссии круга).

Правила входа — те же, что в вердикте монитора: `✓ ГОДЕН`, базис ≥ 0,
OI и окупаемость в пределах порогов пресета. Плечо перп-ноги ≤ 3
(`--leverage`, default 2), нотион считается как `capital / (1 + 1/leverage)`.

Правила выхода (kill-switch):

- funding отрицательный ≥ `--exit-neg` интервалов подряд (default 3);
- убыток > `--max-loss` % капитала (default 5%);
- расхождение дельты ног > 1% (перебалансировка);
- **hold-to-N:** собрано ≥ `--hold-payouts` успешных (положительных) выплат
  (default 2, 0 — выключить) — цель удержания достигнута, фиксируем прибыль.
  Счётчик `payouts` живёт в позиции и растёт в `update_funding` по факту
  закрытых интервалов с положительной ставкой.

### Скальпер (--strategy scalp)

Отдельный режим направленной торговли перпом мейджоров на минутных свечах —
**не** дельта-нейтральная пара, удержание — минуты:

```
python funding_executor.py watch  --strategy scalp --mode paper
python funding_executor.py status --strategy scalp
```

- **Вход:** пересечение `EMA(--scalp-fast=9)` и `EMA(--scalp-slow=21)` на
  последней ЗАКРЫТОЙ свече (`--scalp-interval` 1/3/5 мин): вверх → long,
  вниз → short. Одна перп-нога, одна позиция за раз.
- **Выход:** take-profit / stop-loss по **NET**-базисным пунктам (после
  комиссий тейкера обеих сторон) или по времени (`--scalp-max-hold`, default
  5 мин). Дефолты: `--scalp-tp-bps 20`, `--scalp-sl-bps 15`.
- **Экономика:** перп taker туда-обратно = 11 б.п. (`--scalp-fee-bps` по
  умолчанию `2 × --perp-taker-fee`). Цель обязана перекрывать комиссии — иначе
  скальпинг структурно убыточен.
- **Состояние — отдельное** (`scalp_state.json`): с funding-позицией
  (`position.json`), памятью самообучения и dashboard арбитража не смешивается.
  Рабочий funding-бот не затрагивается.
- `--mode paper` (default) — симуляция по реальным ценам mainnet без ордеров;
  `testnet`/`mainnet` — рыночный/IOC-ордер с защитой `--max-slip-bps`,
  на mainnet нужен `--confirm-live`.

### WebSocket-лента (--ws)

`funding_executor.py watch --ws` заменяет опрос REST пушами ленты (RFC 6455-клиент
на stdlib, [bybit_ws.py](bybit_ws.py)):

- каналы `tickers.*` (linear, snapshot→delta merge) + `orderbook.1.*` (спот, bid/ask);
- автопинг каждые 20 с (`{"op":"ping"}`), реконнект с backoff до 30 с,
  подписки восстанавливаются; лента отвалилась — фолбэк на REST автоматически;
- контроль позиции и риск-выходы проверяются **каждую секунду** без REST,
  поиск кандидатов идёт из памяти ленты (0 REST-запросов в цикле);
- сделки по-прежнему REST. При старте подписываются топ `--prefilter` (60)
  символов по ставке + спот-ноги + символ открытой позиции.

### void — снятие фантомной позиции

Если позиция исчезла на бирже (закрыта руками, ликвидирована), а `position.json`
продолжает её считать: `python funding_executor.py void --force`. Команда
**не отправляет ордеров**, отказывается работать при живом перпе на бирже,
записывает `void` в history и в память (повторные void'ы по символу — пауза 24 ч).
Обычный `close` при фантоме опасен: докупил бы перп-ногу, оставив голый лонг.

### Санитария сделок — физически невозможные результаты (trade_sanity.py)

Экономика пары складывается ровно из трёх слагаемых:
**`итог = funding + (базис_вход − базис_выход) − комиссии круга − проскальзывание`**,
и каждое ограничено: funding приходит раз в интервал ставки (8 ч у BTC/ETH),
базис ходит на десятые доли процента, комиссии круга — расход 0.3–0.5% нотиона.
Поэтому закрытие, у которого **нулевое удержание, ноль полученного funding
и при этом заметный результат**, — не сделка, а дефект учёта (цена ноги взята
из чужого/устаревшего снимка). Прибыль такой записи в точности равна аномалии
цены входа, а не экономике пары. Живой случай: 19 записей ETHUSDT testnet
с `held=0.0 ч`, `funding=$0` и «прибылью» +1.15…+7.4% капитала (+$99.69)
при заявленном проскальзывании входа 190–409 б.п. — они давали панели
несуществующий заработок.

Правило (только очевидное, границы — константы модуля): удержание
< `NO_PAYOUT_H` (0.5 ч — выплат быть не могло), funding ≤ `NO_PAYOUT_FUNDING_EPS`
(поле отсутствует = «неизвестно» — не помечаем) и результат
≥ `GAIN_LIMIT_PCT` (0.5% базы) или ≤ −`LOSS_LIMIT_PCT` (5% — зеркальный дефект:
ложный «убыток» построил бы стоп-лист живому символу). База — нотион, иначе
капитал, иначе обратный счёт из записанного процента, иначе $600.

Помеченная запись (`"suspicious": причина`) **остаётся в файлах** — разбор
аномалии важнее тихого удаления, — но её не считают:

- панель: PnL, винрейт, profit factor, кривая капитала, разбивки по символам
  и времени удержания; сверху — плашка «исключено N сделок на $X» (молчаливое
  исключение выглядело бы как баг расчёта);
- память: скоринг символов, уроки, калибровка, автотюнинг, сравнение
  maker/taker и **стоп-листы** (2 убытка подряд считаются только по
  правдоподобным сделкам);
- `stats` — итоги и последние сделки с пометкой «⚠ подозрительная»;
- при закрытии бот пишет об этом в лог и Telegram — разбирать надо сразу.

Защита работает **на чтении**, поэтому действует сразу после обновления кода,
даже для старых записей без пометки. Разбор накопленного:

```bash
python funding_executor.py sanity        # что исключено, на какую сумму, где
python funding_executor.py sanity --fix  # записать пометку в position.json/memory.json
                                         # (рядом остаётся копия *.pre-sanity.bak)
```

### Ежедневный health-check (healthcheck.py)

Автономный сторож (stdlib, НЕ импортирует код бота — работает, даже если
`funding_executor.py` сломан). Раз в сутки проверяет и шлёт алерт в Telegram, если:

- сервис не `active` (упал / failed);
- сервис в авто-перезапуске (`auto-restart`);
- выросло число перезапусков с прошлого прогона (детект мигающих рестартов);
- лог `watch.log` не обновлялся дольше `--max-log-age` (default 15 мин) —
  сервис «жив», но завис;
- **позиция из `position.json` разошлась с биржей** — тихая потеря ноги (шорт
  снят ликвидацией/руками, спот продан). Проверка автономна (свой подписанный
  GET к Bybit, среда по `mode` записи), поэтому ловит расхождение даже если
  сам бот завис или упал; `--no-position` выключает. Неизвестность (нет
  ключей / сеть) алертом не считается — сравниваются только известные значения;
- **панель слушает не только localhost без пароля** — публичный bind
  (`0.0.0.0`, `::`, внешний IP) без `DASHBOARD_PASSWORD` открывает позицию/PnL
  и кнопки управления всему интернету. Проверяется именно адрес bind (файрвол
  может быть выключен): `--dashboard-port` (default 8050), `--no-bind-check`
  выключает. Панель с паролем и `DASHBOARD_PUBLIC=1` — ок. При публичном bind сервис панели
  автоматически перезапускается, чтобы вернуть loopback; если после рестарта
  панель всё ещё публична — публичный адрес прописан в юните, health-check
  скажет об этом и не будет зацикливать рестарты. Сознательно открытая панель
  с паролем: `DASHBOARD_PUBLIC=1` в `.env` (тогда bind не трогается, а вот
  отсутствие `DASHBOARD_PASSWORD` становится проблемой и алертом).

```bash
python healthcheck.py                # проверка сейчас (алерт только при проблемах)
python healthcheck.py --report-ok    # плюс ежедневное подтверждение «всё ок»
python healthcheck.py --dry-run      # показать, что было бы отправлено
```

**Авто-восстановление (включено по умолчанию):** если сервис числится `active`,
но лог завис (systemd его сам не перезапустит — `Restart=always` ловит только
смерть процесса) — сервис из `--autoheal-services` (default `funding-watch`)
перезапускается, проверяется, что он поднялся и лог ожил, а результат уходит в
Telegram. Отключить: `--no-autoheal`. Позицию health-check по умолчанию НЕ
трогает — при расхождении в алерт добавляется готовая команда
(`void --force` / `close`). С `--fix-position` он приводит ноги в порядок сам
по безопасному правилу: на бирже пусто → `void --force` (без ордеров), любой
реальный остаток → `close` (флэт-действие); защита от ложного срабатывания —
повторная независимая сверка после `--fix-confirm-delay` (default 3 c).

### Живой интеграционный тест сверки (`test_live_check.py`)

Проверяет сверку `position.json` с РЕАЛЬНОЙ биржей одной командой: открывает
позицию на testnet, гоняет health-check (ожидает «совпадает»), намеренно
портит `position.json` (ожидает алерт с расхождением и подсказкой `close`),
закрывает позицию и убеждается, что биржа флэт — всё через те же CLI-команды,
что и у пользователя.

```bash
LIVE_CHECK=1 python test_live_check.py                        # ETHUSDT, $200, 2x
LIVE_CHECK=1 python test_live_check.py --symbol SOLUSDT --capital 150
```

Без `LIVE_CHECK=1` (или `--live`) тест печатает SKIP и ордеров не ставит —
поэтому его можно спокойно держать в пачке `test_*.py`; нет testnet-ключей
→ тоже SKIP. Уже открытая позиция в `position.json` → отказ (тест НЕ
перехватывает боевую позицию). На время теста `funding-watch` best-effort
останавливается и возвращается в конце, health-check зовётся с `--dry-run`
и отдельным `--state`, чтобы не спамить Telegram и не затирать боевой
`health_state.json`. Уборка гарантирована (`finally`): испорченный json
чинится, позиция закрывается.

Анти-спам: тот же набор проблем не повторяется чаще `--realert-hours` (20 ч).
Коды выхода: 0 — ок, 1 — проблемы, 2 — нет ключей Telegram. Состояние
(перезапуски, последний алерт) — в `health_state.json`.

Ставится systemd-таймером `deploy/funding-health.timer` (ежедневно 09:00 UTC,
`Persistent=true` — догоняет пропущенный запуск):

```bash
sudo cp deploy/funding-health.service deploy/funding-health.timer /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now funding-health.timer
systemctl list-timers funding-health.timer
```

### Память самообучения (bybit_memory.py, memory.json)

Исполнитель копит результаты сделок и делает выводы, которых нет в текущих
рыночных данных:

- **скоринг символов**: обновляется из `bot.log` (ENTER/CLOSE/VOID/неудачные входы) и
  прямых вызовов при close/void. Сделки короче 0.5 ч — шум, в скоринг не идут;
- **стоп-лист**: 2 убытка подряд → 7 дней (повтор — 21), 3 неудачных входа
  за сутки или 2 void'а → пауза 24 ч; стоп-лист и приоритет прибыльных символов
  применяются к списку кандидатов в watch;
- **режим входа (maker vs taker)**: сравнивает фактическую прибыль maker-
  и taker-входов (данные `legs`/`slip_bps` в сделках; maker-заполнения страдают
  от adverse selection, поэтому сравнение честное — по PnL). При ≥3 нешумовых
  сделок в каждой группе и разнице ≥0.10 п.п. пишет предпочтение в
  `entry_mode.prefer` — его читает `open_position` (флаг `--taker-only`
  остаётся сильнее памяти). Урок 🧠 — в лог и Telegram при смене режима.

### Единый механизм порогов (калибровка + автотюнинг)

Применяемые пороги фильтра — одна формула:
**`thresholds = base + bias-сдвиг + profit-сдвиг`** (потолки: min_apy30 ≤ 25%,
min_basis ≤ 0.5%, fast_apy ≤ min_apy30). Два независимых вклада:

- **calibrate (bias)** — на каждом старте watch сравнивает прогноз APY при входе
  с фактической годовой доходностью сделки: прогноз систематически завышен →
  пороги вверх, занижен → вниз. Идемпотентно, рестарты не накапливают.
- **autotune (profit-сдвиг)** — раз в 7 дней по фактической прибыли сделок
  периода: окно с хорошей ставкой (apy30 ≥ порога), в котором сделка убыточна
  (финансирование не покрыло комиссии/базис), поднимает min_apy30 (+1 п.п.),
  fast_apy (+0.5), min_basis (+0.05); окупившееся окно (≥10% к нотиону) опускает
  симметрично, пол нуля. Льгота: сделка, закрытая до первой выплаты (funding=0,
  held < интервала funding), убыточна только из-за комиссий — пороги не двигает.
  Внепланово — `memory --autotune`; применить
  сохранённое прямо сейчас (после правки memory.json или relearn) —
  `memory --apply-tune`.

Оба идут через одну пересборку, затирая друг другу пороги невозможно; каждое
фактическое изменение пишется в журнал решений **`threshold_log`** (последние 50,
виден в `memory`, на панели и переживает relearn). Выводы — уроки 🧠 в лог
и Telegram. Мало данных (пороги: ≥5 сделок с прогнозом; ≥5 нешумовых сделок
за период; ≥3+3 для режима входа) — бот ждёт и пишет это в лог.

## Панель (dashboard.py + dashboard_metrics.py)

Панель торговли и метрик. Самодостаточный HTML — без CDN и зависимостей;
формулы вынесены в `dashboard_metrics.py` и тестируются независимо от вёрстки.

```bash
python dashboard.py                  # собрать dashboard.html
python dashboard.py --serve 8050     # сервер с живыми данными: http://127.0.0.1:8050
python dashboard.py --refresh 30     # автообновление раз в 30 сек
python dashboard.py --no-live        # офлайн: без запросов к API
python dashboard.py --data-dir DIR   # читать state из другой папки (тесты)
```

На VPS: `python dashboard.py --serve 8050` — пересобирает панель на каждый
запрос, в браузере всегда свежие данные.

### Доступ по IP:порту (вход по паролю)

```bash
# локально (без пароля, только этот компьютер)
python dashboard.py --serve 8050

# по сети: обязательно с паролем
export DASHBOARD_PASSWORD='сильный-пароль'
python dashboard.py --serve 8050 --host 0.0.0.0
# → http://<IP сервера>:8050  (форма входа, /logout — выход)
```

Публичный bind (`--host 0.0.0.0`) **без пароля не стартует**: панель показывает
позицию, PnL и умеет закрывать позицию, поэтому открытый порт допустим только
со входом. Пароль — `DASHBOARD_PASSWORD` из `.env` (systemd-юнит читает его
сам) или `--password`. Сессия живёт в `HttpOnly`-cookie неделю и **сбрасывается
при рестарте панели** — после перезапуска нужно войти снова. После 5 неверных
попыток с одного IP вход блокируется на 5 минут.

На VPS юнит `deploy/dashboard.service` по умолчанию запускает панель на
localhost (`--host` не указан), и доступ — через SSH-туннель
`ssh -L 8050:127.0.0.1:8050 admin@host`. Публичный bind — отдельное осознанное
решение: `DASHBOARD_PUBLIC=1 DASHBOARD_PASSWORD='...' bash deploy/deploy_vps.sh`
ставит drop-in `deploy/dashboard-public.conf` (bind `0.0.0.0`), пишет пароль и
`DASHBOARD_PUBLIC=1` в `~/bybit-funding/.env` и открывает порт 8050
(`ufw allow 8050/tcp`). `DASHBOARD_PUBLIC=1` говорит health-check, что публичный
bind — сознательный выбор, но только при заданном пароле. Без этого флага
health-check считает публичный bind проблемой и перезапускает панель на
loopback (см. ниже).

### Кнопки управления (режим --serve)

Пульт запускает те же CLI-команды бота отдельным процессом — панель не
торговый робот.

**Безопасные действия** (нужен токен): **закрыть позицию** (`close`), **снять
фантом** (`void --force`), **прогнать health-check**.

**Сервис бота**: **запустить / остановить / перезапустить** — это
`systemctl start|stop|restart funding-watch` (имя сервиса —
`DASHBOARD_BOT_SERVICE`, бинарь — `DASHBOARD_SYSTEMCTL`). На панели виден
текущий статус, кнопки start/stop включаются по нему. Без systemd (Windows,
контейнер) статус — «н/д», а команда вернёт ошибку в отчёте о действии.

**🚨 СТОП-ВСЁ** — одно подтверждённое действие, чтобы гасить всё сразу:
остановить сервис бота и закрыть ВСЕ открытые пары портфеля. Кнопка
всегда активна (даже при статусе «н/д») и, как опасное действие, требует
пароля панели. Порядок шагов зафиксирован: сначала
`systemctl stop funding-watch` — иначе автовход успел бы открыть пару взамен
закрытой, — потом `close --all`, затем сверка факта: `is-active` сервиса и
сколько пар осталось в position.json (кодам возврата на слово не верим).
Список пар перед закрытием перечитывается заново: если бот успел открыть
пару в момент остановки, она тоже попадёт в `close --all` (в отчёте это
видно строкой «портфель изменился, пока бот останавливался»).

Отчёт уходит **не только в браузер**: каждый шаг отдельным сообщением в
Telegram (`TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` — те же ключи, что у бота
и health-check). Сообщения по шагам, а не одним куском в конце: закрытие
портфеля может идти минутами, а «бот остановлен» нужно знать сразу.
В конце отчёт говорит, дошёл ли он до канала («📨 Telegram: отправлено 3 из
3 шагов» либо «не настроен»). Сбой сети/токена действие не ломает: панель
отработает, а в отчёте будет видно, что сообщение не ушло.
Отчёт идёт по шагам «Шаг 1/3 … 3/3» с кодами команд, списком закрытых пар и
итогом («бот остановлен, все пары закрыты» либо «ЕСТЬ ПРОБЛЕМЫ — см. шаги
выше»). Если открытых пар нет — шаг закрытия пропускается с пометкой
«открытых пар нет». Если сервис остановить не вышло — пары всё равно
закрываются (снятие экспозиции важнее), но отчёт прямо предупреждает, что
бот жив и может войти заново, и подсказывает `systemctl start funding-watch`
для возврата.

**▶️ ПУСК-ВСЁ** — обратное действие, тоже с отчётом по шагам. Шаг 1 —
предполётная проверка: портфель обязан быть ПУСТ, иначе кнопка НЕ запускает
бот (с уже открытыми парами он сначала разбирал бы их по своим правилам;
рядовой запуск — кнопка «Запустить бота»). Шаг 2 — `systemctl start` и опрос
`is-active` до ~9 секунд: код 0 у `start` не значит, что процесс жив (юнит с
`Restart=always` успевает моргнуть `failed`). Шаг 3 — сверка автовхода по
факту: `ExecStart` юнита без `--no-auto`, `no-auto` в `config.json` выключен,
а на mainnet в юните есть `--confirm-live` (без него `watch` только
наблюдает). «Сервис active» без этой сверки — не доказательство, что бот
торгует: если `ExecStart` прочитать не удалось, панель так и говорит.
Отчёт по шагам уходит и в Telegram — как у «СТОП-ВСЁ».

**Ручной вход в позицию**: форма с символом, галочкой «войти даже если не
проходит фильтр» (`--force`) и полем «повторите символ». Вызывает
`funding_executor.py enter --symbol X --mode <режим бота>`; на `mainnet`
добавляется `--confirm-live` и требуется отметка «понимаю, что это реальные
деньги». Кнопка выключена, когда свободных слотов нет (`max-positions` в
config.json), а по уже открытой паре вход отклоняется («уже открыт в
портфеле»). Перед ручным входом лучше остановить бота — иначе он может войти
параллельно (executor и сам откажется, если портфель заполнен или пара уже
открыта).

**Портфель**: при `max-positions > 1` каждая пара рисуется отдельной карточкой
со своими кнопками **закрыть** и **снять фантом** (в запрос уходит символ
пары — executor получает `close --symbol X`); health-check остаётся один на
весь портфель.

Защита действий: токен (`DASHBOARD_TOKEN` из `.env` или `--token`; без токена
сервер генерирует случайный и печатает его один раз в консоль — в файл
`dashboard.html` токен не попадает), проверка `Origin` (loopback или тот же
хост, что в заголовке `Host` — поэтому панель по IP работает), ограничение
размера тела запроса и блокировка на параллельный запуск. Токен не задан —
кнопок на панели нет и любые действия запрещены (fail closed). При заданном
`DASHBOARD_PASSWORD` действия дополнительно требуют активной сессии, а
сервисные кнопки, «СТОП-ВСЁ» и ручной вход без пароля запрещены вообще:
они опасные —
вход в панель + токен + подтверждение в форме (символ дважды; для mainnet —
отметка о реальных деньгах).

### Что показывает

**Карточки KPI:** итоговый PnL, винрейт, profit factor, максимальная
просадка, ожидание на сделку, собранный funding, время в рынке, открытая
позиция. При отсутствии сделок панель прямо говорит об этом, а не рисует
нули как «результат».

**Кривая капитала + просадка** — просадка от локального максимума на
отдельной шкале снизу. Итоговый PnL показывает конец истории, а просадка —
насколько глубоко было в минусе по дороге: именно её чувствуешь в реальности.

**PnL по сделкам** — бары вверх/вниз: видны серии убытков (с них память
ставит стоп-лист) и разброс результатов.

**Откуда пришли деньги** — главная диагностика арбитража:
`цена + funding − комиссии`. У дельта-нейтрала «цена» ≈ 0. Показывается
покрытие фандингом (`funding / комиссии`): >1.5 — ставка с запасом отбивает
круг, <1 — стратегия гарантированно теряет на комиссиях, как бы ни выглядели
остальные цифры.

**Здоровье торговли** — profit factor, ожидание, средняя победа/убыток,
худшая и лучшая сделка, recovery factor (заработок на единицу просадки).

**Текущая позиция** — все параметры плюс риск-панель: сколько маржи уже съедено
нереализованным убытком шорта (шкала), сколько до биржевого стопа, какой
убыток будет при его срабатывании, и выставлен ли стоп вообще.

**Разбивка по символам** и **по времени удержания** — на чём стратегия
реально зарабатывает.

**История сделок** — с колонкой «PnL цена»: у корректной пары она ≈ 0,
ненулевое значение означает, что позиция была направленной.

**Память бота** — скоринг символов, применённые пороги, качество прогноза
APY, режим входа (maker/taker), журнал решений порогов, выводы.

**События бота** — последние строки `bot.log` с подсветкой входов, убытков и
тревог. Отдельной строкой сверху: жив ли бот (по времени последнего события)
— иначе тишина панели читается двумя разными способами.

> Sharpe намеренно не считается: у арбитража с редкими крупными сделками
> он крайне неустойчив и обманчив. Profit factor, expectancy и recovery —
> устойчивые и честные метрики.

Для анализа состояния `memory.json` панель читает его напрямую (а не через
`bybit_memory`), чтобы работать даже если бот не запущен.

## Бэктест (backtest.py)

Проверяет пороги **до** того, как они коснутся денег: «если бы бот входил по
текущим правилам последние N месяцев — какой был бы PnL и какая просадка».

```bash
python backtest.py                                  # топ-20 по OI, пресет hold
python backtest.py --symbols BTCUSDT,ETHUSDT,SOLUSDT
python backtest.py --top 30 --preset mainnet
python backtest.py --sweep                          # перебор порогов
python backtest.py --allow-negative-basis --sweep   # разрешить базис < 0
python backtest.py --json report.json               # сохранить отчёт
```

Ключевые команды: `--min-apy30`, `--min-pos`, `--max-breakeven`,
`--hold-payouts`, `--capital`, `--leverage`, `--spread-pct`,
`--allow-negative-basis`.

**Честность бэктеста.** Вердикт пересчитывается на каждом шаге только по
данным, доступным **в тот момент** — будущие ставки не подглядываются.
Вход моделируется по `ask`, выход по `bid`, плюс спред `--spread-pct`.
Funding берётся из фактической истории биржи, а не из прогноза APY. Правила
выхода — те же, что у живого бота (hold-to-N, отрицательные интервалы,
риск маржи).

Поэтому результат **систематически пессимистичен**: реальный maker-вход
проходит лучше, глубина стакана не моделируется, комиссии non-VIP.
Что бэктест НЕ моделирует — перечислено в конце его вывода.

> Бэктест уже окупился: при первом запуске нашёл у себя три бага (начисление
> всей истории выплат разом, потерю причины выхода и асимметрию спреда на
> выходе) — с ними стратегия «показывала» +$208 там, где на самом деле −$84.

**Что он показал на данных осенью 2026:** фандинг на мейджорах Bybit
настолько низкий, что не отбивает комиссию круга (покрытие ~0.02×), а базис
перп/спот стабильно отрицательный (−0.05%), из-за чего правило `basis ≥ 0`
закрывает входы. Текущие пороги пресета `hold` дают **нулевую торговлю** —
и это правильное поведение: ждать надо лучшего окна, а не торговать в убыток.

## Конфиг-файл (config.json)

45 флагов в `ExecStart` systemd — это хрупко (опечатка = сервис не стартует)
и нечитаемо. Торговые параметры вынесены в `config.json`:

```bash
cp config.example.json config.json
python funding_executor.py watch          # читает config.json
python funding_executor.py watch --capital 500   # флаг перекрывает конфиг
python funding_executor.py watch --config /path/to/my.json
```

- значения из командной строки **сильнее** конфига (удобно разово
  переопределить одно число, не правя файл);
- неизвестный параметр в конфиге — понятная ошибка при старте, а не
  молчаливое игнорирование;
- `config.json` содержит только торговые параметры: **секреты в `.env`**;
- портфель: `"max-positions": N` — сколько пар держать одновременно
  (см. «Портфель» выше); `capital` в этом случае — капитал НА ПАРУ.

Файл в `.gitignore`; на VPS создаётся из примера при деплое.

## Ротация bot.log

Бот пишет в `bot.log` напрямую, а journald-ротация systemd на такие файлы
не действует. Ротация встроенная: файл больше **8 МБ** переименовывается в
`.1`, архивы сдвигаются (хранится 5). Перед ротацией хвост свежих записей
переносится в новый файл, чтобы блок «События бота» на панели и
health-check не читали пустой лог.

## Тесты

Все тесты — самодостаточные скрипты на stdlib (pytest не нужен), у каждого свой
код возврата. Единый раннер прогоняет их отдельными процессами и печатает сводку:

```bash
python run_tests.py                  # все test_*.py, краткая сводка
python run_tests.py -v               # с полным выводом каждого теста
python run_tests.py --only dash      # только тесты, чей файл содержит 'dash'
python run_tests.py --live           # плюс живой тест на testnet (РЕАЛЬНЫЕ ордера)
```

Живой тест `test_live_check.py` без `--live`/`LIVE_CHECK=1` печатает SKIP и
ордеров не ставит, поэтому безопасен в общем прогоне. Код возврата раннера: 0 —
провалов нет (SKIP не провал), 1 — есть провалы.

## CI: что проверяется на каждом пуше

`.github/workflows/ci.yml` запускается на **каждый push** в любую ветку, на
pull request и вручную (кнопка «Run workflow»). Три задачи:

| Задача | Что делает | Зачем |
|---|---|---|
| `tests` | `run_tests.py` — все 28 тестов на Python 3.10, 3.12 и 3.14 | 3.10 — нижняя граница, 3.12 — как на VPS, 3.14 — как на рабочей машине |
| `copies` | `compare_copies.py` (коммит ↔ рабочая копия) + `ci/check_repo.sh` | ловит CRLF-дрейф и расхождение байтов, секреты в индексе и файлы, забытые в коммите |
| `vps-drift` | сверка коммита с кодом на сервере | по умолчанию **выключена** (нужны секреты) |

Сторонних зависимостей у тестов нет — только stdlib, поэтому `pip install` в CI
не нужен (paramiko требуется только `deploy/`).

Набор тестов защищён от «тихого» сокращения: если тестовый файл удалили или
забыли закоммитить, задача падает. Ожидаемое число — 28; после осознанного
добавления теста поднимите переменную репозитория `EXPECTED_TESTS`
(Settings → Secrets and variables → Actions → Variables).

Сверка с VPS включается так:

1. Settings → Secrets and variables → Actions → **Secrets**: `VPS_HOST` (IP) и
   `VPS_SSH_KEY` (приватный ключ целиком, `~/.ssh/id_ed25519_bybit`);
2. там же → **Variables**: `ENABLE_VPS_DRIFT=true`.

Без переменной задача пропускается, а не падает.

Локально те же проверки перед пушем:

```bash
bash ci/check_local.sh      # тесты + сверка двух копий + проверки репозитория
bash ci/install_hooks.sh    # повесить их на git pre-push
```

> GitHub Actions должны быть разрешены для аккаунта (Settings → Actions). Если
> API отвечает `Actions has been disabled for this user`, ни один workflow не
> запустится — это ограничение аккаунта, а не репозитория.

## Сверка кода на сервере (`drift_check.py`)

CI вида `vps-drift` смотрит на сервер снаружи. Но чаще всего нужно обратное:
знать **на самом сервере**, не отстал ли его код от того, что запушили с
рабочей машины. Это делает `drift_check.py` плюс таймер `drift-check.timer`
(ежедневно в 10:15, `Persistent=true` — пропущенный день отработает при
следующем включении).

Как работает: у сервера есть **зеркало** `~/bybit-drift/mirror.git`. Локальная
копия отправляет в него свой HEAD при каждом пуше (`ci/publish_mirror.sh`, его
вызывает `pre-push`-хук), а таймер раз в день забирает зеркало в кэш
`~/.cache/bybit-drift/`, распаковывает и сравнивает с `~/bybit-funding` через
`compare_copies.py` — те же правила, что у локальной сверки копий:

- сравниваются только **файлы проекта** (код, тесты, `deploy/`, документация);
- данные прогона и бэкапы (`.env`, `position.json`, `memory.json`, `*.bak`,
  `*.log`, каталог `_bak`) расхождением не считаются;
- отчёт `drift_report.txt` тоже исключён — иначе после первого расхождения
  он сам стал бы «расхождением».

Если хеши разошлись, скрипт пишет отчёт и выходит с кодом 1 — юнит попадает
в `systemctl --failed`, а в Telegram уходит короткий алерт (повтор того же
набора — не чаще раза в сутки). В отчёте по каждому файлу указано, кто новее
и что делать: «разверните» (есть в репозитории, нет на сервере) или «мимо
git» (есть только на сервере). Успешная проверка удаляет старый отчёт,
чтобы он не пугал устаревшим текстом.

```bash
# на сервере — то же, что делает таймер
python3 drift_check.py --quiet
echo $?                       # 0 — сходится; 1 — расхождения; 2 — не смогли получить эталон

# разобраться вручную
systemctl status drift-check --no-pager
cat ~/bybit-funding/drift_report.txt
journalctl -u drift-check -n 30 --no-pager

# сравнить с произвольной папкой (без git) — удобно при разборе
python3 drift_check.py --local /tmp/копия --report /tmp/r.txt
```

Почему не GitHub напрямую: сервер читает эталон из локального зеркала, а не
из репозитория, чтобы сверка не зависела от доступа к GitHub с сервера (в
этом аккаунте git по SSH отдаёт `Repository not found`, а Actions выключены)
и не требовала хранить на сервере никаких токенов. Плата за это — зеркало
обновляется тогда, когда пушит локальная копия; если оно старше недели,
проверка печатает предупреждение, что сравнивает со старым срезом.

Установка (таймер ставит `deploy/deploy_vps.sh`, вручную — так):

```bash
# на рабочей машине: отправить актуальный срез в зеркало
bash ci/publish_mirror.sh

# на сервере: поставить таймер
sudo cp ~/bybit-funding/deploy/drift-check.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now drift-check.timer
systemctl list-timers drift-check.timer --no-pager

# прогнать сейчас, не ждать 10:15
sudo systemctl start drift-check.service; systemctl show -p Result -p ExecMainStatus drift-check.service
```

Эталон — любой git: `drift_check.py --repo <URL> --ref main` (нужен ключ
`--identity`), `--local <папка>` — сверка с обычным каталогом без git.

## Доступ к серверу (SSH)

На VPS **root-логин по SSH выключен**, вход только пользователем `admin` по
ключу, дальше — `sudo -i` при необходимости:

```bash
ssh admin@45.9.18.57        # или ssh bybit-vps (алиас из ~/.ssh/config)
sudo -i                      # root-сессия
```

Политика — в [deploy/sshd-hardening.conf](deploy/sshd-hardening.conf),
ставится как `/etc/ssh/sshd_config.d/00-hardening.conf`:

- `PermitRootLogin no` — root не входит вообще (ключ бесполезен);
- `AllowUsers admin` — единственный вход; список адресов **сознательно не
  ограничен**: домашний IP меняется (за месяц в логах было четыре адреса),
  и жёсткий allowlist запирает доступ при смене сети;
- `PasswordAuthentication no`, `MaxAuthTries 4`, `LoginGraceTime 30`.

Имя `00-*` важно: sshd берёт **первое** значение параметра, а drop-in'ы
подключаются верхней строкой конфига — `50-cloud-init.conf` с
`PasswordAuthentication yes` проигрывает первому файлу, а `99-*.conf`
не переопределил бы ничего.

Брутфорс ограничивает **fail2ban** (`/etc/fail2ban/jail.local`): 4 попытки за
10 минут — бан на 2 часа; свои адреса в `ignoreip`, чтобы опечатка в ключе не
заперла владельца.

Права в системе: не всё работает от `admin` — где нужен root, это указано
явно:

| юнит | пользователь | почему |
|---|---|---|
| `funding-watch` | `admin` | торговому процессу нужен только свой каталог |
| `drift-check` | `admin` | только читает код и зеркало |
| `funding-health` | `root` | умеет чинить публичный bind перезапуском сервиса |
| `dashboard` | `root` | кнопки вызывают `systemctl` для системного юнита |

Каталог проекта — `/home/admin/bybit-funding` (бот и все данные), зеркало для
сверки кода — `/home/admin/bybit-drift/mirror.git`.

> Потеряли доступ? Правку конфига и откат можно сделать из веб-консоли
> хостера: `rm /etc/ssh/sshd_config.d/00-hardening.conf && systemctl reload ssh`.

## Защита при сбоях (для реальных денег)

Всё, что ниже, работает без участия человека — бот не должен терять деньги
из-за своей недоступности.

### Биржевой стоп-лосс на перп-ногу

Все kill-switchы (`--max-loss`, `--max-margin-risk`, дельта-контроль)
**локальные**: они работают, только пока живёт процесс. Если VPS упал,
сеть отвалилась или бот в паузе — единственная защита перп-ноги от
ликвидации это биржа.

Поэтому при входе ставится биржевой стоп (`POST /v5/position/trading-stop`,
`tpslMode=Full`, one-way):

- цена = `вход × (1 + риск)`, где риск берётся из `--max-margin-risk`
  (по умолчанию 70% маржи), минимум 0.5% от входа (иначе выбивает шум);
- срабатывает **без нашего участия** — биржа закрывает ногу сама;
- снимается на выходе (`stopLoss=0`) до закрытия позиции: висящий TP/SL
  иначе может выстрелить по следующей позиции того же символа;
- если биржа отклонила стоп — вход всё равно продолжается (локальные
  выходы работают), но в `status` будет видно «стоп не выставлен»;
- отключить: `--no-exchange-stop`.

Для скальпера стоп считается по `--scalp-sl-bps` и ставится так же.

### Атомарный `position.json`

`position.json` — единственный источник правды о позиции. Запись идёт
через `.tmp` + `os.replace` (+ `fsync`), поэтому падение в середине записи
не оставляет обрезанный JSON. Если файл всё же битый:

- он переименовывается в `position.json.bak` (можно изучить вручную);
- **автовход блокируется** — возможно, на бирже висит позиция, потерянная
  вместе с файлом (иначе получится двойная позиция);
- в Telegram уходит алерт. Вход разблокируется после проверки биржи:
  удалите `.bak`, если позиции на бирже нет.

### Сверка funding с фактическим

Расчётный funding (`ставка × нотион`) — это **модель**. Реальные выплаты
зависят от позиции на момент снимка ставки, частичных закрытий и комиссий.
Поэтому при каждом закрытии (в `testnet`/`mainnet`) бот читает
`/v5/account/transaction-log` и сверяет:

- сходится → в лог `СВЕРКА ... сходится`;
- расхождение > 5 центов или 10% → алерт в Telegram, в сделку пишутся
  `funding_fact` и `funding_diff`.

Это автоматическая проверка того, что PnL-формулы не разъехались с биржой:
на этих же числах учатся `calibrate`/`autotune`.

### Устойчивость к ошибкам биржи

| код | что | поведение |
|---|---|---|
| `10006` | rate limit | 5 попыток с экспоненциальной паузой (0.6с → 8с) + jitter; затем `RateLimited` |
| `10002` | рассинхрон часов | **без ретрая**, `ClockSkew` + алерт «настройте NTP» — подпись не пройдёт, пока часы не починят |
| прочие | ошибка API | сразу исключение с кодом и текстом |
| `URLError` на постановке ордера | ответ потерян | `OrderUnconfirmed`: вход останавливается, автовход блокируется на 30 мин, алерт с командами `close`/`void` |

Последнее — самое важное: раньше обрыв сети при постановке maker-лимитки
считался «вход не удался», бот через 10 минут открывал новую пару, а
висящая лимитка тем временем исполнялась — получался голый шорт.
